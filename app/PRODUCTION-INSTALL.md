# PIM 10.9.3: установка после отдельного подтверждения владельца

Этот пакет подготовлен, но не развёрнут. Он сохраняет прежнюю IndexedDB
`rubizh_pim_v7_launch`, настройки подключения PIM и session keys. Python 3
нужен только терминальному установщику; runtime работает в браузере с IndexedDB.
Все проверки миграции проходят локально до отправки изменений на сервер PIM.
Автоматическая загрузка прайсов заблокирована кодом. Передача на сайт —
только contract v3 (`products[]`, пакеты по 100 моделей, ACK COMMITTED):
PIM отказывается отправлять, пока `GET /api/pim/status` сайта не подтвердит
все версии contract v3, т.е. пока на сайте не применён `install-pim-v3.sh`
и владелец отдельно не включил `'pim_v3_sync'=>true`.

Интерфейс — ровно 5 экранов: НА САЙТ, МОДЕРАЦИЯ, НЕ ПРОХОДИТ, ИМПОРТ, BACKUP.
Новые позиции поставщика без фото при импорте не создают товар (запись
«не проходит: нет фото»). Очистка товаров без фото — только preview →
подтверждение → backup → архив; ничего не удаляется.

## Перед установкой

Закрыть остальные вкладки PIM. В прежней PIM скачать **полную текущую** копию
с документами и журналом, проверить количество товаров. Сохранить файл вне
публичного каталога сайта, например `/home/xk589064/.pim-deploy-backups/input/`.
Не подставлять в эту процедуру старый снимок, если после него были изменения.
Присланная Drive-копия от 04.10 используется для контрольного dry-run и не
доказывает актуальность базы в момент будущей установки.

Пакет распаковать вне сайта. После отдельного подтверждения выполнить:

```bash
python3 /PRIVATE_RELEASE/tools/install-production.py install \
  --archive /PRIVATE_RELEASE/rubizh-pim-10.9.3-final-workflow.zip \
  --target /home/xk589064/rubizh.shop/pim \
  --data-backup /PRIVATE_BACKUPS/current-full-backup.json.gz \
  --backup-root /home/xk589064/.pim-deploy-backups
```

Пути PRIVATE_RELEASE/PRIVATE_BACKUPS — заменить реальными. Установщик проверяет
SHA256 каждого файла, сохраняет прежние файлы и полный data backup вне webroot,
проверяет копию чтением. Ошибка замены автоматически возвращает прежние файлы.
Файлы переключаются атомарно по одному, index.html последним; установка
требует закрытых вкладок. Изменение браузерной/серверной базы CLI не выполняет.

## Миграция данных

Первый запуск читает текущую локальную базу **без** автоматической починки,
перевода, изменения цен, публикации, архивации или cloud pull/push.
Сначала migration dry-run, затем кнопка «Повна копія файлом + застосувати».
До записи полный snapshot всех KV, неизвестных ключей, фото-ссылок, документов
с бинарными файлами и localStorage сохраняется в отдельную backup IndexedDB
`rubizh_pim_release_backups_v1`, проверяется SHA256/чтением и скачивается.
Перед применением нужно вручную подтвердить сохранение
скачанного файла — сам браузер не предоставляет надёжного подтверждения записи.
Отмена/ошибка backup/изменение другой вкладкой прекращает миграцию.
Не подтверждать сохранение до появления файла на диске.

При успешном применении сохраняются ID, SKU, supplier records, цены и
вычисленные цены, фото, ручные ограничения, публикационные флаги и прежние
категории. Добавляются отсутствующие approved canonical categories, policies,
accepted classification/size metadata. Уже нормализованные записи переносятся
без пересчёта. Catalogues/exceptions существующей базы сохраняются; конфликт
останавливает миграцию вместо потери данных. Неподтверждённый Tactical Belt
остаётся UNKNOWN. Семантика RC не меняется. Повторное применение — no-op.

Новый браузер без существующей базы не создаёт пустой каталог: можно получить
существующую серверную базу кнопкой «Отримати існуючу базу з сервера» при
сохранённом подключении. Этот явный pull разрешён только в пустую локальную
базу без pending changes, ничего не отправляет на сервер; затем требуется
migration preview и полный backup. Альтернатива — полная
копия через `/release-recovery.html`, затем migration preview. Не использовать
для восстановления копию старее текущей базы без проверки владельцем.
Если серверная база содержит более новые изменения, сначала синхронизировать
их и экспортировать полный backup **в прежней PIM**, до переключения файлов.

## Правила цен (действие владельца)

Миграция и запуск цены не меняют. Передача на сайт (contract 3) требует утверждённых правил:
обычные товары 30%, выплата поставщику от 10 000 грн — 25%, позиция комплекта — 20%, скидки не ниже
15% после доната. Если в базе ещё прежние настройки (например 24 / 15 / 15), экран «НА САЙТ»
показывает блок «Правила цен не применены». После migration нажать «Проверить правила цен»,
просмотреть список изменений и «Применить». Перед записью создаются полная автокопия и
`safety/before_pricing_30_25_20`, запись проверяется; последующие правки владельца не сбрасываются.

## Rollback — данные и файлы

1. Закрыть остальные вкладки. В «Резервные копии» нажать rollback. Перед ним
   создаётся полная rescue-копия текущих данных; отмена её сохранения блокирует
   rollback. Восстанавливаются исходные данные, operational sync/feed gates
   остаются false. Для сервера PIM сохраняются актуальные CAS versions, чтобы
   старый backup не перезаписал новые серверные изменения без проверки.
2. Если основной интерфейс неисправен, открыть `/release-recovery.html` на
   **том же домене**, выбрать сохранённый полный snapshot и восстановить его.
   Recovery не отправляет запросов в сеть; сервер PIM не откатывается этим шагом.
3. В терминале вернуть прежние файлы:

```bash
python3 /PRIVATE_BACKUP/install-production.py rollback --backup /PRIVATE_BACKUP
```

PRIVATE_BACKUP — путь BACKUP_PATH, выданный установщиком. Сначала восстановить
данные при доступной странице recovery, затем вернуть прежние файлы; новые
recovery/lib файлы при code rollback удалятся, если прежде отсутствовали.
Серверная PIM синхронизация после rollback требует отдельного запуска прежней
PIM и разрешения CAS conflicts; никакой автоматической массовой перезаписи
удалённой базы или сайта rollback не делает. Full backup хранит чувствительные
настройки, его нельзя коммитить или размещать в открытом webroot.
