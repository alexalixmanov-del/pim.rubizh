# Категоризация РУБІЖ — 10.7.0

Категория поставщика и категория магазина теперь хранятся отдельно. Справочник содержит ровно 134 ID из задания; поставщик не может автоматически расширить дерево магазина. Название и путь — представление, ID — постоянный идентификатор.

## Переход существующего каталога

1. Сохраните свежий JSON backup действующей PIM и установите новую сборку на прежний адрес.
2. Откройте «Інструменти і налаштування» → «Категоризація» → «Dry run міграції». До подтверждения каталог не меняется.
3. Просмотрите «Конфлікт правил» и «Без категорії». Можно выбрать категорию для товара или подтвердить соответствие для всех товаров одной категории конкретного поставщика. Эти решения пока входят в план. Повторный dry run сбрасывает неприменённый план.
4. Нажмите «Застосувати перевірену міграцію». PIM автоматически создаёт полный внутренний JSON backup с предложением миграции, применяет решения, сравнивает защищённые данные и независимо проверяет записанную базу. При ошибке возвращает прежнее состояние.
5. Перезагрузите PIM и проверьте итог. «Завантажити звіт JSON» выгружает справочник, все старые пути, mappings, aliases, правила, результаты проверки, неизвестные позиции, противоречия и ручные назначения.

Неизвестные позиции можно оставить для дальнейшей проверки: они сохраняются целиком, не архивируются и не создают публичную категорию. Новым неизвестным товарам назначается `canonical_category_id=null`, `NEEDS_REVIEW`. Ранее подтверждённая категория сохраняется при неопределённом новом импорте; появляется предупреждение `SUPPLIER_CATEGORY_CHANGED`. Полная синхронизация сохраняет ID ранее опубликованных неизвестных товаров в `all_ids`, чтобы магазин не скрыл их из-за пропуска в обновлении.

## Ручная работа и обучение

Приоритет: ручная категория → подтверждённое соответствие конкретного поставщика → соответствие пути → правила категории с проверкой контекста → название → предложение из описания или характеристики → проверка человеком. Confidence — оценка надёжности правила, а не статистически калиброванная вероятность. Автоматическое совпадение принимается от 0.95. Подтверждённый supplier mapping допускается от 0.80; слабое описание остаётся предложением.

Общие группы уточняются названием внутри совместимого типа: «Головні убори» + «Балаклава», «Взуття» + «Берці», «Шоломи» + «Кавер». Прямое противоречие «Рюкзаки» + «Підсумок для аптечки» остаётся `CONFLICT_REVIEW`. Компонент в названии «Штани з наколінниками» не заменяет основной тип товара. «Магазин» требует контекста оружия или калибра; «плита» без бронезащиты не является бронеплитой.

«Підтвердити» сохраняет ручную категорию одного товара. «Створити mapping» сохраняет правило выбранного поставщика. Если одинаковый лист встречается под разными родителями (например «Зимние» у курток и штанов), правило и массовое применение дополнительно ограничиваются исходным полным путём. «Застосувати до всіх…» сохраняет это правило и пересчитывает подходящие товары, защищая ручные назначения. Ошибка записи откатывает категории, очередь и правило. Кнопки в карточке позволяют перейти к полю категории и сохранить подтверждённое правило вместе с карточкой.

## Что сохраняется

Исходные название, категория, путь, подкатегория и ID поставщика сохраняются в предложениях и `category_sources`; представитель источника также доступен в полях карточки. XML сохраняет полный путь наряду с листом категории. RU/UA, апострофы, тире, варианты написания и отдельные транслитерации нормализуются для сравнения.

Атрибуты, извлечённые классификатором, хранятся в `canonical_attributes`: пол, сезон, материал, камуфляж, класс защиты, размер бронеплиты. Ручные характеристики остаются в `attrs`; при публикации ручные значения имеют приоритет при совпадающем ключе.

Категоризация не меняет закупку, РРЦ, цену, минимальную маржу, остатки и предзаказ. Старые ценовые правила по категориям продолжают использовать `pricing_category_path`, сохранённый до переноса. Новые правила, которые администратор явно выбирает в редакторе цен после миграции, привязываются к каноническому ID; их изменения видны в ценовом предпросмотре. Категория не используется как основание для объединения вариантов. Изменившийся артикул можно связать по уникальному ID предложения; общий ID нескольких вариантов не используется вслепую.

История решения включает товар, прежнюю и новую категорию, источник, правило, время и пользователя. Категории в таблице, карточке и массовых действиях используют один канонический механизм; отмена табличного изменения восстанавливает ID и источник решения.

## Магазин

Каталог содержит `canonical_category_id` и справочник `{id,name,parent_id,path}`. Сырой путь поставщика не публикуется. После подтверждённой миграции синхронизация требует объявленной поддержки `canonical_category_version=1`, подтверждения хэша справочника и точного ID категории каждого записанного товара. Без этого POST не выполняется либо результат не считается успешно сохранённым.

Сервер магазина отсутствует в переданных исходниках. Требуемый контракт описан в [server-contract.md](server-contract.md). Обновление PIM не обновляет сервер магазина. До его поддержки нового контракта API-публикация канонических категорий блокируется с понятным сообщением; локальная работа PIM доступна.

## Проверка

Полная копия предоставленного каталога проверена в изолированном хранилище: 3 113 товаров и 8 734 варианта сохранены, изменения цен и остатков из-за миграции — 0. Данные по пяти поставщикам восстановлены из backup и импортированы дважды: повторный импорт не создаёт новых карточек/вариантов и сохраняет цены, остатки, ID категорий и ручные решения. Оригинальные XLSX/XML поставщиков не предоставлены и не заявляются проверенными.

Бесплатный модуль работает локально: платные AI-API не нужны. Не все неопределённые товары можно достоверно классифицировать по доступным данным. Такие позиции видны в очереди; назначение наугад не выполняется.
